## 1. Background

Phase 2E-5 investigates how transliteration capabilities should be represented and accessed within the AksaraNusantara architecture.

The preceding experiments established a progressively more detailed understanding of capability architecture:

- Capability Discovery
- Capability Access
- Capability State
- Capability Ownership
- Capability Lifecycle
- Access Boundary
- Execution Semantics
- Failure Classification
- Preconditions vs Execution Failure
- State Check vs Execution Boundary
- Boundary Communication

The experiments demonstrated that capability architecture cannot be adequately represented by a simple boolean such as:

```text
available = True
```

Capability representation involves several conceptual dimensions.

One important distinction emerged between:

1. **Execution State**
2. **Failure Classification**

These concepts may appear similar because both are relevant when an operation does not produce a successful result.

However, they answer different architectural questions.

**Execution State** answers:

> What happened to the execution process?

**Failure Classification** answers:

> What explains the unsuccessful outcome or non-execution condition?

Step 14 was created to determine whether these concepts should remain separate.

---

# 2. Research Question

The primary research question is:

> Should Execution State and Failure Classification be represented as separate concepts?

A related question is:

> Does every unsuccessful transliteration request represent an execution failure?

Previous experiments suggested that the answer may be **no**.

For example:

```text
Capability unavailable
```

does not necessarily mean:

```text
Execution failed
```

because the execution process may never have started.

The distinction therefore requires explicit architectural investigation.

---

# 3. Initial Conceptual Model

Before the experiment, three execution states were proposed:

```text
NOT_EXECUTED
SUCCESS
FAILED
```

These values describe the outcome of the execution process.

Separately, three failure classifications were proposed:

```text
CAPABILITY_UNAVAILABLE
INVALID_INPUT
EXECUTION_ERROR
```

These values describe the reason associated with an unsuccessful request or execution condition.

The initial model was therefore:

```text
Execution State
        +
Failure Classification
```

rather than a single status enumeration containing every possible outcome.

---

# 4. Hypothesis

The initial hypothesis was:

> Execution State and Failure Classification represent different dimensions of execution information and should therefore remain separate.

The proposed mapping was:

| Situation | Execution State | Failure Classification |
|---|---|---|
| Capability unavailable | `NOT_EXECUTED` | `CAPABILITY_UNAVAILABLE` |
| Invalid input | `FAILED` | `INVALID_INPUT` |
| Runtime execution error | `FAILED` | `EXECUTION_ERROR` |
| Successful execution | `SUCCESS` | `None` |

The experiment was designed to determine whether this separation produced a clearer and more accurate architectural model.

# 6. Execution State Model

The experiment defined three execution states:

```text
NOT_EXECUTED
SUCCESS
FAILED
```

These states describe what happened to the execution process.

---

## 6.1 `NOT_EXECUTED`

```text
NOT_EXECUTED
```

means:

> The requested operation did not enter the execution process.

The operation was blocked before actual execution began.

Example:

```text
Capability unavailable
```

Result:

```text
State   : NOT_EXECUTED
Failure : CAPABILITY_UNAVAILABLE
```

The important point is that the operation was not attempted.

Therefore:

```text
NOT_EXECUTED
```

must not automatically be interpreted as:

```text
FAILED
```

---

## 6.2 `SUCCESS`

```text
SUCCESS
```

means:

> The requested operation executed successfully.

Example:

```text
State   : SUCCESS
Output  : [Transliterated] hanacaraka
Failure : None
```

A successful execution does not require a failure classification.

---

## 6.3 `FAILED`

```text
FAILED
```

means:

> Execution was attempted but did not complete successfully.

The experiment tested two examples:

```text
INVALID_INPUT
```

and:

```text
EXECUTION_ERROR
```

The representation is therefore:

```text
State   : FAILED
Failure : <specific classification>
```

This preserves two different pieces of information:

```text
FAILED
```

describes **what happened** to execution.

The failure classification describes **why it did not succeed**.

---

# 7. Failure Classification Model

The experiment defined three failure classifications:

```text
CAPABILITY_UNAVAILABLE
INVALID_INPUT
EXECUTION_ERROR
```

Unlike `ExecutionState`, these values do not describe the execution lifecycle itself.

They provide additional classification information associated with a non-successful request or execution condition.

---

## 7.1 `CAPABILITY_UNAVAILABLE`

```text
CAPABILITY_UNAVAILABLE
```

represents a situation in which the requested capability cannot currently be used.

Example:

```text
Transliteration capability is not available
```

The critical architectural observation is:

```text
CAPABILITY_UNAVAILABLE
```

does not necessarily imply:

```text
FAILED
```

because the execution process may never have started.

The tested representation is:

```text
State   : NOT_EXECUTED
Failure : CAPABILITY_UNAVAILABLE
```

---

## 7.2 `INVALID_INPUT`

```text
INVALID_INPUT
```

represents an unsupported or invalid input condition.

The experimental model treats this case as occurring after the execution boundary has been reached and processing has begun.

Therefore:

```text
State   : FAILED
Failure : INVALID_INPUT
```

This distinction is part of the experimental model and should not yet be interpreted as a final production validation contract.

---

## 7.3 `EXECUTION_ERROR`

```text
EXECUTION_ERROR
```

represents an unexpected failure occurring during execution.

Example:

```text
Unexpected transliteration failure
```

The resulting representation is:

```text
State   : FAILED
Failure : EXECUTION_ERROR
```

The execution state remains general:

```text
FAILED
```

while the separate classification communicates the specific failure category.

# 11. Result Analysis

The experiment supports a separation between:

```text
Execution State
```

and:

```text
Failure Classification
```

The tested model is:

| Execution State | Failure Classification | Meaning |
|---|---|---|
| `NOT_EXECUTED` | `CAPABILITY_UNAVAILABLE` | Execution never started |
| `FAILED` | `INVALID_INPUT` | Execution did not succeed because of input |
| `FAILED` | `EXECUTION_ERROR` | Execution encountered an unexpected error |
| `SUCCESS` | `None` | Execution completed successfully |

The important observation is that these two dimensions provide different information.

For example:

```text
FAILED
```

alone does not explain why execution failed.

The additional classification:

```text
INVALID_INPUT
```

or:

```text
EXECUTION_ERROR
```

provides that distinction.

Likewise:

```text
CAPABILITY_UNAVAILABLE
```

does not necessarily indicate that execution failed, because the execution process may not have begun.

---

# 12. The Critical Distinction: `NOT_EXECUTED` vs `FAILED`

The most important finding of Step 14 is:

```text
NOT_EXECUTED ≠ FAILED
```

These states represent different points in the execution lifecycle.

---

## 12.1 `NOT_EXECUTED`

Conceptually:

```text
REQUEST
   │
   ▼
Capability Check
   │
   ├── Capability unavailable
   │
   ▼
Execution blocked
```

Result:

```text
NOT_EXECUTED
```

The execution process never started.

---

## 12.2 `FAILED`

Conceptually:

```text
REQUEST
   │
   ▼
Capability available
   │
   ▼
Execution begins
   │
   ▼
Failure occurs
   │
   ▼
FAILED
```

The execution process began, but it did not complete successfully.

Examples:

```text
FAILED
+
INVALID_INPUT
```

or:

```text
FAILED
+
EXECUTION_ERROR
```

---

## 12.3 Why the Distinction Matters

The distinction may become important for:

- diagnostics
- logging
- UI feedback
- error reporting
- capability APIs
- testing
- future service boundaries

A system that collapses both states into:

```text
FAILED
```

would lose information about whether execution was ever attempted.

# 14. Architectural Insight

The primary architectural insight from Step 14 is:

> Execution State and Failure Classification should be treated as separate information dimensions.

The conceptual model can therefore be expressed as:

```text
Execution Result
=
Execution State
+
Optional Output
+
Optional Failure Classification
+
Optional Diagnostic Information
```

This is conceptually different from a single enumeration such as:

```text
SUCCESS
CAPABILITY_UNAVAILABLE
INVALID_INPUT
EXECUTION_ERROR
...
```

The single-enumeration approach mixes different categories of information.

Some values describe:

```text
execution outcome
```

while others describe:

```text
failure cause
```

The separated model preserves these dimensions independently.

---

# 15. Why a Single Status Is Insufficient

Consider the following conceptual status model:

```text
SUCCESS
FAILED
CAPABILITY_UNAVAILABLE
INVALID_INPUT
EXECUTION_ERROR
```

The problem is that these values are not equivalent kinds of information.

For example:

```text
SUCCESS
```

describes an execution outcome.

Whereas:

```text
INVALID_INPUT
```

describes a reason.

And:

```text
CAPABILITY_UNAVAILABLE
```

may describe a condition in which execution never started.

Therefore the values exist at different conceptual layers.

A separated representation is more expressive:

```text
State   : FAILED
Failure : INVALID_INPUT
```

versus:

```text
State   : NOT_EXECUTED
Failure : CAPABILITY_UNAVAILABLE
```

This distinction would be difficult to preserve cleanly if everything were represented as one flat status enumeration.

---

# 16. Preliminary Architectural Principle

Based on the experimental evidence, the following preliminary principle is proposed:

> Execution outcome and failure cause should not be collapsed into the same conceptual layer unless a specific architectural requirement requires such simplification.

This is a **research conclusion**.

It is not yet a production API specification.

The exact representation of these concepts may evolve during subsequent Transliteration Architecture Research.

In particular, this experiment does not establish:

- final enum names
- final public API signatures
- final result object implementation
- final exception model
- final serialization format
- final UI representation

Those decisions remain outside the scope of Step 14.

---

# 17. Evidence Boundary

Step 14 establishes a specific architectural finding:

```text
Execution State
        ≠
Failure Classification
```

The experiment does **not** establish that the currently tested values are the complete production vocabulary.

Specifically, the experiment does not prove that:

```text
NOT_EXECUTED
```

can only occur because of:

```text
CAPABILITY_UNAVAILABLE
```

Nor does it prove that:

```text
CAPABILITY_UNAVAILABLE
```

is the only possible classification associated with non-execution.

Therefore the evidence boundary is:

```text
Validated:
Separation of execution outcome and failure classification.

Not yet validated:
Complete taxonomy of non-execution reasons.
```

This distinction is important for preventing experimental terminology from prematurely becoming production architecture.

# 18. Open Questions

Step 14 leaves an important question unresolved:

> Does every `NOT_EXECUTED` state necessarily correspond to `CAPABILITY_UNAVAILABLE`?

The current evidence does not establish this.

Potential future situations may include:

```text
PRECONDITION_NOT_MET
```

```text
EXECUTION_BLOCKED
```

```text
REQUEST_CANCELLED
```

or other conditions in which execution does not begin.

This leads to a broader research question:

> Should failure classification include a broader category of non-execution reasons?

Another possible conceptual direction is:

```text
Execution State
│
├── NOT_EXECUTED
│      └── Non-Execution Reason
│
├── SUCCESS
│
└── FAILED
       └── Failure Classification
```

However, this is a research hypothesis only.

It must not yet be promoted to the production API.
