## 1. Objective

Step 21 investigates whether `ExecutionRequest` requires an intrinsic lifecycle state model such as:

```text
RequestState
├── CREATED
├── ACCEPTED
├── QUEUED
├── DEFERRED
├── REJECTED
└── CANCELLED
```

The purpose is not to design or implement `RequestState`, but to determine whether such an abstraction is semantically required by the architecture discovered so far.

The research follows the established methodology:

```text
Research Question
    ↓
Hypothesis
    ↓
Experimental Model
    ↓
Isolated Experiment
    ↓
Run Test
    ↓
Inspect Output
    ↓
Architectural Finding
    ↓
Documentation
```

---

# 2. Research Context

Previous research established several distinct concepts:

```text
Operation
    ↓
ExecutionRequest
    ↓
Admission Decision
    ↓
Execution
    ↓
ExecutionResult
```

Step 20 additionally established that pre-execution orchestration concepts such as queueing and deferred execution should not automatically be interpreted as execution states.

Step 21 therefore investigates the boundary around `ExecutionRequest` itself.

The central question is:

> Does Request Lifecycle constitute an intrinsic state machine of `ExecutionRequest`, or can lifecycle information be represented through admission decisions and orchestration observations/events external to the Request?

---

# 3. Overall Hypothesis

### H21

> Request lifecycle information does not require an intrinsic `RequestState` semantic primitive. Lifecycle information can be represented through Admission Decisions and Orchestration Events/Observations while preserving Request Identity, Operation Identity, and the separation from Execution Identity.

This hypothesis is tested through six isolated probes.

---

# 4. Step 21-1 — Request Lifecycle Identity Probe

## Research Question

> Does Request Identity remain stable across different lifecycle conditions?

## Experimental Scope

The experiment represented:

```text
CREATED
ACCEPTED
QUEUED
DEFERRED
REJECTED
CANCELLED
```

as lifecycle observations associated with the same `ExecutionRequest`.

## Result

```text
12 tests
12 PASS
0 FAIL
```

## Evidence

The experiment demonstrated that:

1. A Request has identity at creation.
2. Lifecycle observations preserve Request Identity.
3. One Request may have multiple lifecycle observations.
4. Lifecycle observations do not change Operation Identity.
5. Lifecycle identity is independent of Execution Identity.
6. A Request may reach a terminal lifecycle condition without an Execution Identity.

## Finding

> Request Identity is independent of Request Lifecycle representation.

Lifecycle observations may describe the condition of a Request without becoming part of the Request's intrinsic identity.

---

# 5. Step 21-2 — Request State vs Admission Decision

## Research Question

> Are `ACCEPTED` and `REJECTED` states of the Request, or are they Admission Decisions?

## Models Compared

### Model A

```text
ExecutionRequest
       │
       └── RequestState
             ├── ACCEPTED
             └── REJECTED
```

### Model B

```text
ExecutionRequest
       │
       └── AdmissionDecision
             ├── ACCEPTED
             └── REJECTED
```

## Result

```text
12 tests
12 PASS
0 FAIL
```

## Evidence

The experiment demonstrated:

- Request exists before an admission decision.
- Admission does not create Request Identity.
- `ACCEPTED` is not an Execution State.
- `REJECTED` is not an Execution State.
- An accepted Request may exist without an Execution.
- A rejected Request may exist without an Execution.
- Admission does not change Operation Identity.
- Request Identity can remain stable across different admission observations.

The experiment also demonstrated that identical vocabulary does not imply identical semantics:

```text
ExperimentalRequestState.ACCEPTED
```

and:

```text
ExperimentalAdmissionDecision.ACCEPTED
```

share the same name but represent different semantic concepts.

## Finding

> `ACCEPTED` and `REJECTED` are adequately represented as Admission Decisions and do not require membership in `ExecutionState`.

The experiment provides evidence against treating admission results as intrinsic execution semantics.

# 6. Step 21-3 — Request State vs Orchestration Event

## Research Question

> Are `QUEUED`, `DEFERRED`, and `CANCELLED` intrinsic Request States, or can they be represented as orchestration events/observations?

## Models Compared

### Model A

```text
ExecutionRequest
       │
       └── RequestState
             ├── QUEUED
             ├── DEFERRED
             └── CANCELLED
```

### Model B

```text
ExecutionRequest
       │
       └── OrchestrationEvent
             ├── REQUEST_QUEUED
             ├── REQUEST_DEFERRED
             └── REQUEST_CANCELLED
```

## Result

```text
13 tests
13 PASS
0 FAIL
```

## Evidence

The experiment demonstrated:

- Request can exist without an orchestration event.
- Orchestration events do not create Request Identity.
- Orchestration events do not change Operation Identity.
- Multiple events can be associated with the same Request.
- Orchestration events can exist before Execution.
- `QUEUED` does not mean Execution has started.
- `DEFERRED` does not mean Execution has failed.
- `CANCELLED` can occur before Execution.
- Observation of an event does not require mutation of the Request.

## Finding

> Orchestration events provide a viable semantic representation of Request lifecycle conditions without requiring an intrinsic `RequestState`.

This does not establish that production must use event sourcing or an event-driven architecture. It establishes only that lifecycle semantics can exist independently from Request State.

# 7. Step 21-4 — Request Lifecycle Cardinality

## Research Question

> Does one Request have exactly one lifecycle condition, or can it have multiple lifecycle observations over time?

## Result

```text
12 tests
12 PASS
0 FAIL
```

## Evidence

The experiment demonstrated:

```text
1 Request → N Lifecycle Observations
```

For example:

```text
Request
   ├── CREATED
   ├── ACCEPTED
   └── QUEUED
```

More importantly, repeated lifecycle conditions are representable:

```text
QUEUED
   ↓
DEFERRED
   ↓
QUEUED
```

The same Request Identity remains present throughout the sequence.

Lifecycle history can also be empty:

```text
Request
   │
   └── Lifecycle History = []
```

## Finding

> Request lifecycle has potentially one-to-many cardinality.

Therefore lifecycle history cannot be equated directly with a single current Request State.

A state representation may describe a current condition, but it does not inherently represent lifecycle history.

# 8. Step 21-5 — Request Terminal-State Probe

## Research Question

> Are `REJECTED` and `CANCELLED` intrinsically terminal states of Request, or is terminality an interpretation of lifecycle information?

## Result

```text
13 tests
13 PASS
0 FAIL
```

## Evidence

The experiment demonstrated:

- `REJECTED` can be interpreted as terminal.
- `CANCELLED` can be interpreted as terminal.
- Neither requires an Execution Identity.
- Terminal lifecycle conditions do not destroy Request Identity.
- Terminal lifecycle conditions do not change Operation Identity.
- Terminal conditions can coexist with `NOT_EXECUTED`.
- Terminal observations can be stored as lifecycle history.
- Terminality can be determined from lifecycle observations without a Request State object.

Conceptually:

```text
Lifecycle Observation
        │
        ↓
Terminal Interpretation
```

rather than necessarily:

```text
ExecutionRequest.state = TERMINAL
```

## Finding

> Terminality is not proven to be an intrinsic property of `ExecutionRequest`.

It can instead be interpreted from lifecycle information according to the applicable orchestration semantics.

# 11. Consolidated Architectural Finding

The combined evidence supports the following statement:

> **Request Lifecycle does not require `RequestState` as a semantic primitive.**

Lifecycle information can be represented through distinct semantic mechanisms:

```text
ExecutionRequest
       │
       ├── AdmissionDecision
       │       ├── ACCEPTED
       │       └── REJECTED
       │
       └── OrchestrationEvent(s)
               ├── CREATED
               ├── QUEUED
               ├── DEFERRED
               └── CANCELLED
```

while Execution remains a separate boundary:

```text
ExecutionRequest
       │
       ├── Admission / Orchestration
       │
       └── Execution
              │
              ↓
        ExecutionResult
```

# 12. Semantic Distinctions Established

Step 21 strengthens the following distinctions:

```text
Request Identity
        ≠
Request Lifecycle
        ≠
Admission Decision
        ≠
Orchestration Event
        ≠
Execution Identity
        ≠
Execution Result
```

In particular:

```text
Request State
        ≠
Admission Decision
```

and:

```text
Request State
        ≠
Orchestration Event
```

The same vocabulary, such as `ACCEPTED` or `CANCELLED`, must not be assumed to represent the same semantic object merely because the labels are identical.

# 15. Architectural Principle

The strongest principle emerging from Step 21 is:

> **Do not introduce intrinsic Request State merely to represent observations produced by admission or orchestration.**

More formally:

```text
Lifecycle Information
        ↓
Ask first:
"What semantic source produced this information?"
        ↓
Admission?
Orchestration?
Execution?
Observation?
        ↓
Only introduce intrinsic state
if semantic evidence requires it.
```

This preserves the separation between:

```text
Entity Identity
Decision
Event
Execution
Result
```

# 21. Final Research Finding

Step 21 establishes a stronger semantic boundary around `ExecutionRequest`:

```text
ExecutionRequest
    │
    ├── Identity
    │
    ├── Admission Decision
    │
    ├── Orchestration Observations
    │
    └── Execution Relationship
```

rather than:

```text
ExecutionRequest
    │
    └── RequestState
          └── everything that happens to the Request
```

The research therefore supports the following architectural principle:

> **An entity should not own a state merely because conditions can be observed about that entity. Before introducing intrinsic state, identify whether the condition actually belongs to the entity or originates from an external decision, orchestration process, or execution boundary.**

This principle is broader than transliteration and may have implications for the future general Capability Architecture of AksaraNusantara.
