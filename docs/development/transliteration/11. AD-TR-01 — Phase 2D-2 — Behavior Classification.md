# 1. Latar Belakang



Phase 2D-1 telah menghasilkan inventarisasi terhadap berbagai kontrak dan behavior transliterasi.



Namun inventarisasi saja belum cukup untuk menentukan test.



Pertanyaan berikutnya adalah:



> **Jenis kontrak apakah yang sedang kita hadapi?**



Sebuah behavior dapat terlihat penting, tetapi belum tentu harus diuji sebagai public API.



Sebaliknya, sebuah aturan arsitektural mungkin sangat penting bagi proyek, tetapi tidak tepat diuji melalui `assert output == expected_output`.



Karena itu, Phase 2D-2 berfokus pada klasifikasi behavior sebelum test boundary ditentukan.



---



# 2. Tujuan Phase 2D-2


Klasifikasi ini digunakan untuk menentukan:



```text

What must be tested

        ↓

        ↓

        ↓

```

# 3. Kategori A — Public Behavior



Public Behavior adalah behavior yang dapat diamati dari luar subsystem.



Bentuk konseptualnya:



```text

Input

    ↓

Public API

    ↓

Observable Result

```



Kategori ini merupakan kandidat utama untuk Core Test Contract.



---



## 3.1 Input Kosong



Behavior:



```text

""

 ↓

""

```



Status:



> 🟢 Stable



Input kosong harus dapat ditangani secara deterministic tanpa memerlukan interpretasi orthographic.



---



## 3.2 Deterministic Output



Prinsip:



```text

Same Input

+

Same Configuration

        ↓

Same Output

```



Status:



> 🟢 Stable



Transliteration tidak boleh menghasilkan output berbeda secara acak untuk input dan konfigurasi yang sama.



---



## 3.3 Whitespace Preservation



Whitespace merupakan bagian dari input yang harus dipertahankan sesuai contract yang telah dibahas.



Contoh konseptual:



```text

Input

A   B



        ↓



Output

A   B

```



Status:



> 🟢 Stable



---



## 3.4 Unknown General Characters



Karakter umum yang tidak menjadi bagian dari transliteration mapping tidak boleh hilang begitu saja.



Prinsip:



```text

Known character

    → transliterated



Unknown general character

    → preserved

```



Status:



> 🟢 Stable sebagai prinsip preservation



Catatan:



Kebijakan khusus untuk karakter yang secara linguistik dianggap invalid tetap dapat berada pada area lain.



---



## 3.5 Explicit Transliteration Direction



Arah transliterasi harus menjadi operasi yang jelas.



Konseptual:



```text

Latin

  ↓

Javanese

```



berbeda dari:



```text

Javanese

  ↓

Latin

```



Status:



> 🟢 Stable



Direction bukan hasil tebakan UI atau side effect dari presentation layer.



---



## 3.6 No External Side Effect



Core transliteration operation tidak boleh:



- menulis ke storage;

- melakukan persistence;

- mengubah learning history;

- bergantung pada UI;

- menghasilkan side effect eksternal.



Status:



> 🟢 Stable



---



# 4. Kategori B — Architectural Contract



Architectural Contract adalah aturan mengenai pembagian tanggung jawab.



Kategori ini tidak selalu memiliki bentuk:



```python

assert result == expected

```



Yang dilindungi adalah boundary dan ownership.



---



# 4.1 ScriptPack Ownership



Data linguistik spesifik terhadap aksara dimiliki oleh:



```text

ScriptPack

```



Bukan:



```text

TransliterasiTab

```



Dan bukan:



```text

Hard-coded dictionary

di application layer

```



Prinsip:



```text

Script-specific linguistic knowledge

        ↓

ScriptPack

```



---



# 4.2 Layer Separation



Alur arsitektural yang harus dipertahankan:



```text

UI

 ↓

Application

 ↓

Core / Transliteration Boundary

 ↓

ScriptPack

```



UI tidak boleh menjadi lokasi utama logic transliterasi.



---



# 4.3 Internal Responsibility Separation



Secara konseptual, transliteration pipeline dapat memiliki tanggung jawab:



```text

Tokenizer

    ↓

Mengenali input



Resolver

    ↓

Menentukan role berdasarkan context



Composer

    ↓

Membentuk output

```



Namun pembagian ini tidak berarti seluruh komponen harus diekspos sebagai public API.



---



# 4.4 Architectural Testing



Architectural contract dapat dilindungi melalui:



- integration tests;

- boundary tests;

- dependency discipline;

- code review.



Tidak semua architectural rule harus berubah menjadi test terhadap private implementation.



---



# 5. Kategori C — Implementation Detail



Implementation Detail adalah keputusan internal yang tidak boleh dikunci terlalu dini oleh public test contract.



Contohnya:



```text

Nama class Token

```



```text

Enum TokenType

```



```text

Struktur internal token

```



```text

Algoritma scanning

```



```text

Loop atau recursion

```



```text

Jumlah helper method

```



```text

Urutan internal processing

```



---



## Prinsip



Jika implementasi dapat berubah:



```text

Implementation A

        ↓

same public behavior

        ↑

Implementation B

```



maka test contract sebaiknya tidak mengunci detail perbedaannya.



---



# 6. Kategori D — Open Decision



Open Decision adalah behavior yang belum memiliki expected behavior final.



Area ini tidak boleh dipaksa menjadi executable contract.



---



## 6.1 Invalid Token Sequence



Belum seluruh recovery behavior diputuskan.



Pertanyaan yang masih terbuka:



- apakah error dikembalikan?

- apakah karakter dipertahankan?

- apakah sebagian sequence diproses?

- bagaimana diagnostic direpresentasikan?



---



## 6.2 Invalid Javanese Orthography



Belum seluruh invalid orthographic sequence memiliki policy recovery final.



---



## 6.3 Complete Ambiguity Table



Belum seluruh ambiguous Latin sequence telah memiliki mapping final.



---



## 6.4 Lookahead Rules



Kebutuhan lookahead telah diidentifikasi, tetapi seluruh policy resolver belum otomatis menjadi contract final.



---



## 6.5 Syllable Boundaries



Aturan formal mengenai seluruh boundary belum ditetapkan sebagai public contract.



---



## 6.6 Murda Automatic Selection



Belum ada keputusan final bahwa transliteration engine harus melakukan automatic Murda selection.



---



## 6.7 Rekan Automatic Selection



Policy automatic selection untuk Rekan belum menjadi contract final.



---



## 6.8 Number Formatting



Kebijakan lengkap mengenai transliterasi dan formatting angka belum final.



---



## 6.9 Strict Round-Trip Identity



Prinsip berikut belum diasumsikan:



```text

Latin

  ↓

Javanese

  ↓

Latin

=

Original Latin Input

```



Karena transliteration dan orthographic interpretation dapat bersifat lossy atau context-dependent.
