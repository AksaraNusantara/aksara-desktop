## 1. Research Objective

Step 18 investigates the correct conceptual boundary between:

1. a generic capability contract,
2. capability-specific semantics,
3. execution semantics,
4. operation identity, and
5. execution-result representation.

The objective is not to define production interfaces.

Instead, the objective is to determine which concepts appear to be invariant across capability domains and which concepts should remain capability-specific.

The research follows the established methodology:

> Research Question → Hypothesis → Experimental Model → Isolated Experiment → Run Test → Inspect Output → Architectural Finding → Documentation → Next Step

---

# 2. Research Question

The primary research question for Step 18 is:

> **If execution semantics are generic, where is the correct boundary between Generic Capability Contract and Capability-Specific Contract?**

The research was subsequently decomposed into five experiments:

- **18-1 — Contract Boundary Matrix**
- **18-2 — Execution Ownership Probe**
- **18-3 — Operation Boundary Probe**
- **18-4 — Capability Identity vs Operation Identity Probe**
- **18-5 — Execution vs Execution Result Boundary Probe**

---

# 3. Hypothesis

### H18

> A generic capability contract should contain only semantics that remain invariant across capability domains, while capability-specific contracts should own operation-specific input, output, and domain semantics.

The research additionally examines whether execution should belong directly to a capability contract or whether execution should be treated as a generic execution-layer concern.

A secondary hypothesis was:

> Capability, Operation, Execution, and ExecutionResult may represent distinct conceptual levels, but conceptual distinction does not automatically imply separate production abstractions.

---

# 4. Experimental Scope

The experiments are deliberately synthetic.

They do not import or modify production AksaraNusantara modules.

They use isolated models and Python standard-library `unittest`.

The experiments therefore provide architectural evidence, not implementation requirements.

# 5. Experiment 18-1 — Contract Boundary Matrix

## 5.1 Research Question

> Which concerns appear to belong to a generic capability contract, and which concerns remain capability-specific?

## 5.2 Experimental Comparison

The experiment classified candidate concerns into two conceptual groups.

### Generic candidates

- Capability identity
- Execution state
- Non-execution classification
- Failure classification
- Diagnostic semantics

### Capability-specific candidates

- Input shape
- Operation parameters
- Output representation
- Domain-specific rules

## 5.3 Result

Test execution:

```text
Ran 11 tests in 0.002s

OK
```

## 5.4 Finding

The experiment demonstrated that generic and capability-specific concerns can be separated conceptually.

The following distinction is supported:

```text
Generic Contract
    ├── Capability Identity
    ├── Execution Semantics
    ├── Failure Semantics
    ├── Non-Execution Semantics
    └── Diagnostic Semantics

Capability-Specific Contract
    ├── Input
    ├── Operation Parameters
    ├── Output
    └── Domain Rules
```

### Architectural Principle

> **Generic Contract ≠ Specific Operation Contract**

The generic layer should not absorb operation-specific data merely because the operation is executed through the same execution mechanism.

# 6. Experiment 18-2 — Execution Ownership Probe

## 6.1 Research Question

> Is execution semantics part of the capability contract, or can execution be represented by a generic execution layer outside the capability contract?

## 6.2 Experimental Models

### Model A — Capability-Owned Execution

```text
Capability
    │
    └── execute()
          │
          ▼
       Outcome
```

### Model B — Generic Execution Layer

```text
Capability
    │
    ▼
Generic Execution Layer
    │
    ▼
Execution Outcome
```

## 6.3 Result

Test execution:

```text
Ran 11 tests in 0.001s

OK
```

## 6.4 Finding

Both models can represent the same execution semantics.

Model B provides an important architectural observation:

```text
Capability
    ├── Execution #1 → SUCCESS
    ├── Execution #2 → FAILED
    └── Execution #3 → NOT_EXECUTED
```

The capability itself does not need to change merely because different execution occurrences produce different outcomes.

This supports a conceptual separation between:

```text
Capability Contract
    ├── Identity
    ├── Domain Operation
    ├── Domain Input
    └── Domain Output

Generic Execution Model
    ├── State
    ├── NonExecutionReason
    ├── FailureClassification
    └── Diagnostic
```

## 6.5 Architectural Caution

This experiment does **not** establish that AksaraNusantara must implement a separate execution service or execution layer.

It establishes only that execution semantics are capable of being modeled independently from capability-specific semantics.

# 7. Experiment 18-3 — Operation Boundary Probe

## 7.1 Research Question

> Is an Operation a meaningful conceptual boundary between Capability and Execution?

## 7.2 Experimental Models

Three models were compared.

### Model A

```text
Capability
    ↓
Execution
```

### Model B

```text
Capability
    ↓
Operation
    ↓
Execution
```

### Model C

```text
Capability
    ↓
Operation Definition
    ↓
Execution Instance
```

## 7.3 Result

Test execution:

```text
Ran 12 tests in 0.002s

OK
```

## 7.4 Finding

All three models can represent equivalent execution semantics.

However, an important architectural observation emerged:

> **A single capability may expose multiple operations.**

For example:

```text
Transliteration Capability
    ├── transliterate
    ├── validate
    └── normalize
```

Therefore, the concept of Operation can be meaningful independently of the Capability itself.

## 7.5 Architectural Caution

The existence of an Operation concept does not justify introducing multiple implementation layers automatically.

Additional abstraction must be justified by semantic necessity, not merely by structural elegance.

# 8. Experiment 18-4 — Capability Identity vs Operation Identity Probe

## 8.1 Research Question

> Are Capability, Operation, and Execution distinct identity concepts?

## 8.2 Result

Test execution:

```text
Ran 12 tests in 0.002s

OK
```

## 8.3 Finding

The experiment provides evidence for three conceptual identity levels:

```text
Capability Identity
        ≠
Operation Identity
        ≠
Execution Identity
```

Their conceptual meanings are:

```text
Capability
    = capability or domain available

Operation
    = action provided by that capability

Execution
    = one occurrence/use of that operation
```

Example:

```text
cap.transliteration
│
├── op.transliterate
│      ├── exec.001 → SUCCESS
│      ├── exec.002 → FAILED
│      └── exec.003 → NOT_EXECUTED
│
└── op.validate
       ├── exec.004 → SUCCESS
       └── exec.005 → FAILED
```

## 8.4 Important Observation

The same operation can have multiple execution occurrences.

For example:

```text
op.transliterate
    │
    ├── exec.001 → SUCCESS
    ├── exec.002 → FAILED
    └── exec.003 → NOT_EXECUTED
```

Therefore:

> Operation identity is not equivalent to execution identity.

Likewise, the same operation name appearing under two different capabilities does not necessarily imply identical operation identity.

## 8.5 Architectural Principle

> **Capability Identity ≠ Operation Identity ≠ Execution Identity**

## 8.6 Architectural Caution

This is a conceptual distinction.

It does not automatically require three separate classes, registries, database entities, or public APIs.

> **Conceptual distinction ≠ Implementation abstraction**

# 9. Experiment 18-5 — Execution vs ExecutionResult Boundary Probe

## 9.1 Research Question

> Do Execution and ExecutionResult have distinct semantic identities, or can they be represented as one concept without losing architectural clarity?

## 9.2 Experimental Models

### Model A — Distinct Concepts

```text
Execution
    │
    └── produces
            │
            ▼
      ExecutionResult
```

Conceptually:

```text
Execution
    execution_id
    operation_id

ExecutionResult
    execution
    state
    output
    failure
    non_execution_reason
    diagnostic
```

### Model B — Unified Concept

```text
ExecutionResult
    execution_id
    operation_id
    state
    output
    failure
    non_execution_reason
    diagnostic
```

## 9.3 Result

Test execution:

```text
Ran 12 tests in 0.002s

OK
```

## 9.4 Finding

Both models successfully represented:

- execution identity,
- operation identity,
- SUCCESS,
- FAILED,
- NOT_EXECUTED,
- failure classification,
- non-execution reason,
- diagnostic,
- output.

Therefore:

> **Both distinct and unified models can express the same observable execution semantics.**

## 9.5 Important Observation

The distinct model provides an additional conceptual possibility:

```text
Execution
    │
    │
    │  occurrence exists conceptually
    │
    ▼
ExecutionResult
```

An Execution can therefore be represented independently from its result.

However, the experiment does not establish that AksaraNusantara requires such separation.

The unified model remains semantically sufficient for the tested result model.

## 9.6 Architectural Principle

> **Execution and ExecutionResult are semantically distinguishable, but their separation is not yet proven to be architecturally mandatory.**

This is an important boundary.

We have evidence for distinction, but not evidence strong enough to freeze two production abstractions.

# 13. Architectural Principles Derived

## Principle 1 — Capability Purpose Does Not Define Execution Semantics

A capability may be:

- transformational,
- action-oriented,
- persistence-oriented,
- query-oriented,
- discovery-oriented.

Yet its execution lifecycle can still use the same generic semantic model.

> **Capability Purpose ≠ Execution Semantics**

---

## Principle 2 — Execution Semantics Should Remain Capability-Agnostic

The following concepts have demonstrated cross-capability applicability:

```text
SUCCESS
FAILED
NOT_EXECUTED
FailureClassification
NonExecutionReason
Diagnostic
```

They should therefore not be designed around transliteration-specific assumptions.

---

## Principle 3 — Output Semantics Remain Capability-Specific

The execution model can be generic while outputs remain specialized.

Examples:

```text
Transliteration
    → transformed text

Audio Playback
    → playback information

Progress Persistence
    → persistence information

Character Lookup
    → character information

Capability Discovery
    → capability information
```

Therefore:

> **Generic execution does not imply generic output.**

---

## Principle 4 — Non-Execution Is Boundary-Based

A capability being unavailable, a precondition failing, or execution being blocked are meaningful in terms of whether the operation crossed the execution boundary.

The classification is therefore not intrinsically tied to transliteration.

---

## Principle 5 — Diagnostic Is Observational

Diagnostic information can vary independently from:

- execution state,
- failure classification,
- non-execution reason,
- output.

Therefore diagnostic information should not be used as the semantic classification itself.

---

## Principle 6 — Capability, Operation, and Execution Have Distinct Conceptual Identities

The evidence supports:

```text
Capability Identity
    ≠
Operation Identity
    ≠
Execution Identity
```

This should remain a conceptual invariant unless future research provides evidence requiring a different model.

---

## Principle 7 — ExecutionResult Is an Observable Semantic Boundary

ExecutionResult provides the externally meaningful description of an execution outcome.

It can contain:

```text
state
output
failure
non-execution reason
diagnostic
```

Whether it must be implemented as a separate abstraction from Execution remains unresolved.

---

## Principle 8 — Conceptual Distinction Does Not Automatically Require Implementation Abstraction

This principle is particularly important for preventing premature architecture:

> **Conceptual distinction ≠ Implementation abstraction**

A concept should become a production abstraction only when its independent identity provides architectural value.

---

# 14. Decision

Step 18 establishes the following provisional architectural decision.

## Accepted

The architecture should conceptually distinguish:

```text
Capability
    ↓
Operation
    ↓
Execution
    ↓
ExecutionResult
```

and should distinguish generic execution semantics from capability-specific semantics.

## Accepted Generic Semantics

The generic execution model may contain:

```text
ExecutionState
FailureClassification
NonExecutionReason
Diagnostic
Execution Identity
```

## Accepted Capability-Specific Semantics

Capability-specific contracts may own:

```text
Input
Operation Parameters
Output
Domain Rules
```

## Not Yet Decided

The following remain deliberately unfrozen:

```text
Whether Execution requires a production class
Whether ExecutionResult requires a production class
Whether Execution owns execution
Whether a GenericExecutionLayer should exist
Whether Operation requires a production abstraction
```

These decisions require implementation-oriented evidence later.

> **Capability, Operation, Execution, and ExecutionResult are useful conceptual distinctions, but the research does not yet justify forcing each distinction into a separate production abstraction.**

# 19. Limitations

The evidence is based on synthetic models.

The experiments demonstrate semantic representability, not production performance or implementation cost.

In particular:

1. A separate Execution abstraction may become valuable when lifecycle, tracing, cancellation, scheduling, or persistence requirements are introduced.
2. A unified ExecutionResult may remain sufficient if execution occurrences do not need independent representation.
3. Operation may or may not require an independent production object.
4. The generic execution model may evolve when real application workflows are introduced.
5. Future experiments may invalidate or refine these provisional boundaries.

Therefore, the findings should remain architectural guidance rather than irreversible implementation rules.
