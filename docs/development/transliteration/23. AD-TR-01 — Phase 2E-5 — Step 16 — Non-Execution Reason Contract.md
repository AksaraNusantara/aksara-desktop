# 2. Background

Step 14 established that:

```text
Execution State
```

and:

```text
Failure Classification
```

are separate architectural concepts.

The experiment established three execution states:

```text
NOT_EXECUTED
SUCCESS
FAILED
```

where:

```text
NOT_EXECUTED
=
The execution process never started.
```

while:

```text
FAILED
=
The execution process started but did not succeed.
```

and:

```text
SUCCESS
=
The execution process completed successfully.
```

Step 14 also introduced failure classifications such as:

```text
CAPABILITY_UNAVAILABLE
INVALID_INPUT
EXECUTION_ERROR
```

with the observation that `CAPABILITY_UNAVAILABLE` may correspond to:

```text
NOT_EXECUTED
```

rather than:

```text
FAILED
```

This distinction was subsequently expanded in Step 15.

Step 15 demonstrated that multiple different conditions may lead to:

```text
NOT_EXECUTED
```

including experimental candidates such as:

```text
CAPABILITY_UNAVAILABLE
PRECONDITION_NOT_MET
EXECUTION_BLOCKED
REQUEST_CANCELLED
```

These were explicitly treated as experimental vocabulary rather than production API values.

Therefore, a new architectural question emerged:

> Does every `NOT_EXECUTED` result require an explicit `NonExecutionReason`?

---

# 3. Research Question

The primary research question for Step 16 is:

> **What should the contract semantics be for `NonExecutionReason` when the execution state is `NOT_EXECUTED`?**

More specifically:

1. Is a reason mandatory?
2. May a reason be absent?
3. What does an explicitly unknown reason mean?
4. Does a consumer require the reason in order to interpret the result?
5. Does the requirement depend on the consumer?
6. Is `NonExecutionReason` part of the execution state itself, or additional information associated with that state?

---

# 5. Candidate Contract Models

Three primary models were investigated.

## 5.1 Model A — Mandatory Reason

Under Model A:

```text
NOT_EXECUTED
    ↓
NonExecutionReason REQUIRED
```

Therefore:

```text
NOT_EXECUTED + reason
```

is valid, while:

```text
NOT_EXECUTED + None
```

would be considered incomplete.

The motivation for this model is that a non-execution state should always explain why execution did not begin.

---

## 5.2 Model B — Optional Reason

Under Model B:

```text
NOT_EXECUTED
    ↓
NonExecutionReason OPTIONAL
```

Therefore both are representable:

```text
NOT_EXECUTED + reason
```

and:

```text
NOT_EXECUTED + None
```

The motivation is that execution state and explanatory information have different availability requirements.

The system may know that execution did not occur without necessarily knowing or exposing the reason.

---

## 5.3 Model C — Explicit UNKNOWN

Under Model C:

```text
NOT_EXECUTED
    ↓
NonExecutionReason REQUIRED
```

but the reason may explicitly be:

```text
UNKNOWN
```

Therefore:

```text
NOT_EXECUTED + PRECONDITION_NOT_MET
```

and:

```text
NOT_EXECUTED + UNKNOWN
```

are valid, while:

```text
NOT_EXECUTED + None
```

would represent an incomplete contract.

The motivation is to distinguish:

```text
reason is unknown
```

from:

```text
reason information is absent
```

# 6. Experimental Sequence

Step 16 was investigated through a sequence of focused architecture probes.

---

## 6.1 Step 16A — Basic Reason Requirement

The first experiment examined whether the basic result structure could represent:

```text
NOT_EXECUTED + known reason
```

as well as alternative representations where the reason was absent or explicitly unknown.

The experiment successfully represented the candidate models.

### Observation

The data structure alone does not select a contract model.

Therefore:

```text
representable
```

does not imply:

```text
architecturally valid
```

This established the need for semantic experiments.

---

## 6.2 Step 16B — Non-Execution Result Invariants

The next experiment tested combinations of:

```text
ExecutionState
NonExecutionReason
FailureClassification
Output
```

The experiment demonstrated that the underlying experimental structure was capable of representing combinations that may be semantically questionable.

For example:

```text
SUCCESS + NonExecutionReason
```

or:

```text
NOT_EXECUTED + FailureClassification
```

could be represented by the data model.

### Observation

The data model is more permissive than the intended semantic model.

Therefore:

> **Structural representability is insufficient to define execution-result validity.**

Semantic invariants must exist independently of the raw data structure.

---

## 6.3 Step 16C — Semantic Validity

The next experiment examined the semantic relationship between execution state and the associated information.

The experiment established the following distinctions:

```text
NOT_EXECUTED
=
Execution did not start.
```

```text
FAILED
=
Execution started but did not succeed.
```

```text
SUCCESS
=
Execution completed successfully.
```

The experiment further established that:

```text
NonExecutionReason
```

is semantically relevant to:

```text
NOT_EXECUTED
```

while:

```text
FailureClassification
```

is semantically relevant to:

```text
FAILED
```

and not to:

```text
SUCCESS
```

### Architectural observation

The conceptual relationship is therefore:

```text
ExecutionState
      │
      ├── NOT_EXECUTED
      │       └── NonExecutionReason
      │
      ├── SUCCESS
      │       └── Output
      │
      └── FAILED
              └── FailureClassification
```

This is a semantic model rather than merely a structure-definition model.

---

## 6.4 Step 16D — UNKNOWN Reason Semantics

The experiment investigated whether:

```text
None
```

and:

```text
UNKNOWN
```

have the same meaning.

The experiment demonstrated that they can represent different semantic situations.

Conceptually:

```text
None
=
Reason information is absent or unavailable.
```

while:

```text
UNKNOWN
=
A reason is conceptually expected, but the actual reason is explicitly unknown.
```

Therefore:

```text
None ≠ UNKNOWN
```

### Important limitation

This distinction demonstrates semantic usefulness.

It does **not** demonstrate that `UNKNOWN` must become a production enumeration value.

---

## 6.5 Step 16E — Information Loss

The next experiment investigated whether a consumer can distinguish:

```text
known reason
```

from:

```text
UNKNOWN
```

and:

```text
None
```

The experiment demonstrated that the three states can carry different information.

Conceptually:

```text
PRECONDITION_NOT_MET
        ↓
Known reason
```

```text
UNKNOWN
        ↓
Reason explicitly unknown
```

```text
None
        ↓
Reason information absent
```

### Observation

Using `None` does not inherently mean that the execution state is unknown.

The consumer can still know:

```text
NOT_EXECUTED
```

while not knowing why.

---

## 6.6 Step 16F — Consumer Requirement

The next experiment changed perspective from the result producer to the result consumer.

A basic consumer may require only:

```text
ExecutionState
```

For example:

```text
if state == NOT_EXECUTED:
    show("Execution did not start")
```

Such a consumer does not require a reason.

A reason-aware consumer may instead use:

```text
ExecutionState
+
NonExecutionReason
```

and can benefit from:

```text
known reason
UNKNOWN
None
```

### Architectural observation

The need for `NonExecutionReason` can depend on the consumer's responsibility.

Therefore:

> **A consumer may require reason information without proving that every producer must always provide it.**

---

## 6.7 Step 16G — Contract Completeness

A further experiment examined whether a proposed contract could be described as complete.

The experiment revealed an important methodological issue:

> A test that defines `NOT_EXECUTED` as requiring a reason inside its own validation logic cannot independently prove that the reason is mandatory.

In other words, if the test contains:

```text
NOT_EXECUTED → reason REQUIRED
```

as part of the validator itself, then the test is partly circular.

### Architectural lesson

Contract completeness must be evaluated against independent architectural requirements rather than against a validator that already assumes the desired conclusion.

This prevents:

```text
Hypothesis
    ↓
Validator
    ↓
PASS
    ↓
"Therefore hypothesis is proven"
```

from becoming circular reasoning.

---

## 6.8 Step 16H — Information Sufficiency

The next investigation asked:

> What minimum information does a consumer independently need to understand a `NOT_EXECUTED` result?

The experiment separated two questions:

```text
WHAT happened?
```

and:

```text
WHY did it happen?
```

The execution state answers:

```text
NOT_EXECUTED
```

and therefore communicates:

```text
WHAT:
Execution did not start.
```

A reason, when present, communicates:

```text
WHY:
The execution did not start for this reason.
```

This distinction allows:

```text
NOT_EXECUTED + reason
```

and:

```text
NOT_EXECUTED + None
```

to carry different amounts of information without changing the fundamental execution state.

---

## 6.9 Step 16I — Reason-Aware Consumers

The subsequent investigation considered consumers whose behavior depends on the cause of non-execution.

Examples include conceptual consumers that may want to distinguish:

```text
CAPABILITY_UNAVAILABLE
```

from:

```text
PRECONDITION_NOT_MET
```

or:

```text
EXECUTION_BLOCKED
```

Such consumers require more information than a consumer that only needs to know whether execution occurred.

### Observation

Reason information is therefore useful and, for some consumers, necessary.

However:

```text
consumer requirement
```

and:

```text
universal producer requirement
```

remain separate architectural questions.

---

## 6.10 Step 16J — Consumer-Dependent Requirement

The investigation then examined whether the requirement for reason information is universal.

The result indicates that the answer depends on the consumer's responsibility.

A minimal consumer can operate with:

```text
NOT_EXECUTED
```

alone.

A diagnostic or recovery-oriented consumer may require:

```text
NOT_EXECUTED
+
NonExecutionReason
```

### Architectural finding

The existence of a reason-aware consumer does not automatically justify making the reason mandatory for every execution result.

---

## 6.11 Step 16K — Model Comparison

The three candidate models were compared:

| Model | `NOT_EXECUTED` | Reason absent | Explicit `UNKNOWN` |
|---|---|---|---|
| Model A | Reason mandatory | Invalid/incomplete | Not required |
| Model B | Reason optional | Valid | Possible |
| Model C | Reason mandatory | Invalid/incomplete | Explicitly supported |

The experiments demonstrated that all three models are technically representable.

The experiments did not produce independent evidence sufficient to declare one of the three models universally mandatory.

Therefore the model comparison remains an architectural evaluation rather than a direct experimental proof.

---

## 6.12 Step 16L — Architectural Requirement Trace

The final investigation compared the candidate requirement against the existing architecture.

The current ScriptPack specification establishes that transliteration is a writing-system-specific capability and that the Core Engine does not currently define a standardized transliteration interface.

The existing architecture therefore does not currently contain an approved production requirement stating:

```text
Every NOT_EXECUTED result MUST contain
a NonExecutionReason.
```

Consequently, such a requirement cannot be declared an existing architectural contract.

# 8. Architectural Findings

## 8.1 Execution State Answers "What Happened?"

The primary execution state remains:

```text
NOT_EXECUTED
SUCCESS
FAILED
```

The state communicates the outcome of the execution process.

In particular:

```text
NOT_EXECUTED
```

means:

> The execution process did not begin.

This information is independent of whether the reason is known.

---

## 8.2 NonExecutionReason Answers "Why?"

When available,:

```text
NonExecutionReason
```

provides additional explanation for:

```text
NOT_EXECUTED
```

Conceptually:

```text
ExecutionState
        +
NonExecutionReason
```

provides more information than:

```text
ExecutionState
```

alone.

However, the additional information is not necessarily always available.

---

## 8.3 Reason Availability and Execution State Are Different Dimensions

The research supports the distinction:

```text
Execution State
```

versus:

```text
Reason Information Availability
```

For example:

```text
NOT_EXECUTED + PRECONDITION_NOT_MET
```

means:

```text
Execution did not start.
Reason is known.
```

while:

```text
NOT_EXECUTED + None
```

means:

```text
Execution did not start.
Reason information is absent or unavailable.
```

The execution state remains unambiguous in both cases.

# 9. Model Evaluation

## 9.1 Model A — Mandatory Reason

### Advantages

- Every `NOT_EXECUTED` result is immediately explainable.
- Diagnostic consumers receive a consistent information structure.
- Producers are forced to identify a cause.

### Risks

- The producer may not actually know the cause.
- It may encourage artificial values merely to satisfy the contract.
- It may force `UNKNOWN` or equivalent values into the production model.
- It may make a simple execution-state consumer dependent on information it does not need.

### Current assessment

```text
Plausible
but not proven mandatory.
```

---

## 9.2 Model B — Optional Reason

### Advantages

- Separates execution outcome from explanatory information.
- Allows the system to report `NOT_EXECUTED` even when the reason is unavailable.
- Avoids inventing diagnostic information.
- Supports simple consumers naturally.
- Allows reason-aware consumers to use additional information when available.

### Risks

- Some consumers may need to handle absent reason information.
- Diagnostic consistency may be lower if producers provide different levels of detail.

### Current assessment

```text
Architecturally compatible
with the evidence obtained so far.
```

This is currently the least restrictive model supported by the research evidence.

---

## 9.3 Model C — Explicit UNKNOWN

### Advantages

- Distinguishes:

```text
reason unknown
```

from:

```text
reason information absent
```

- Provides a structured representation for incomplete diagnostic knowledge.

### Risks

- Introduces another semantic value.
- May create pressure to define `UNKNOWN` in the production enum.
- Requires a clear rule for when `UNKNOWN` must be used instead of `None`.

### Current assessment

```text
Semantically useful
but not proven necessary.
```

---

# 10. Architectural Interpretation

The strongest conclusion supported by the experiments is not:

```text
Model A
```

or:

```text
Model B
```

or:

```text
Model C
```

as a final production decision.

The stronger conclusion is the separation of concepts:

```text
Execution State
        ≠
Non-Execution Reason
```

The relationship can be expressed as:

```text
ExecutionResult
│
├── ExecutionState
│
├── Output
│
├── FailureClassification
│
├── NonExecutionReason
│
└── Diagnostic Information
```

with semantic applicability:

```text
NOT_EXECUTED
    └── NonExecutionReason

SUCCESS
    └── Output

FAILED
    └── FailureClassification
```

The exact cardinality and mandatory/optional rules remain a later contract-design decision.

# 11. Decision Boundary

Step 16 establishes the following research conclusion:

> **The current architecture does not provide sufficient evidence to mandate a `NonExecutionReason` for every `NOT_EXECUTED` result.**

Therefore:

```text
NOT_EXECUTED
```

must be understood as independently meaningful.

A reason may provide additional information:

```text
NOT_EXECUTED
    +
reason
```

but absence of the reason does not automatically invalidate:

```text
NOT_EXECUTED
```

---

# 12. Provisional Contract

For future architectural work, the following model is provisionally preferred:

```text
ExecutionResult
│
├── ExecutionState        REQUIRED
│
├── Output               applicable to SUCCESS
│
├── FailureClassification applicable to FAILED
│
└── NonExecutionReason   applicable to NOT_EXECUTED
                         but availability not yet mandated
```

Conceptually:

```text
SUCCESS
    → Output

FAILED
    → FailureClassification

NOT_EXECUTED
    → NonExecutionReason, when available
```

This is a **provisional research contract**, not yet a production API contract.

---

# 13. Semantics of `None` and `UNKNOWN`

The research establishes a useful semantic distinction:

```text
None
```

may mean:

> No reason information is available or supplied.

Whereas:

```text
UNKNOWN
```

may mean:

> A reason is conceptually expected, but the actual reason is explicitly unknown.

Therefore:

```text
None ≠ UNKNOWN
```

However, the research does **not** require `UNKNOWN` to become a production enumeration value.

The production representation may instead choose another mechanism, such as:

```text
None
```

plus diagnostic metadata, or another future representation.

That decision belongs to a later API-contract stage.

---

# 14. What Step 16 Does NOT Decide

Step 16 does not define:

- the final Python class for `ExecutionResult`;
- the final enum for `ExecutionState`;
- the final enum for `NonExecutionReason`;
- whether `UNKNOWN` becomes a production enum value;
- whether `None` is the final representation of missing reason information;
- the final error/diagnostic object;
- the final public ScriptPack transliteration interface;
- whether `NonExecutionReason` belongs inside or outside a standardized execution-result abstraction;
- changes to AN-STD-001 §17;
- production implementation.

These remain future design decisions.

# 15. Relationship to Existing ScriptPack Architecture

The findings remain consistent with the existing architectural direction.

The ScriptPack architecture is intended to accommodate writing-system-specific capabilities, while the Core Engine remains independent of specific writing systems.

Transliteration is currently treated as an optional capability whose standardized interface remains reserved for future specification.

Therefore, Step 16 does not introduce a new production requirement into the Core Engine.

Instead, it supplies architectural evidence for a future standardized execution-result model.

---

# 16. Architectural Principle

The following principle is proposed as a research conclusion:

> **Execution outcome and explanatory information should remain conceptually separate. A `NOT_EXECUTED` state may be meaningful even when the reason for non-execution is unavailable.**

This can be summarized as:

```text
WHAT happened?
    ↓
ExecutionState

WHY did it happen?
    ↓
NonExecutionReason
```

The second dimension enriches the first but does not redefine it.

# 18. Conclusion

Step 16 completes the investigation into the contract semantics of non-execution reasons.

The research journey can now be summarized:

```text
STEP 14
Execution State
        ≠
Failure Classification
        ↓
STEP 15
Multiple Non-Execution Reasons
        ↓

```

The resulting conceptual model is:

```text
                    Execution
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ▼             ▼             ▼
    NOT_EXECUTED      SUCCESS       FAILED
          │             │             │
          ▼             ▼             ▼
   Reason when       Output       Failure
    available                     Classification
```

The most important conclusion is:


A:

```text

```

provides additional explanatory information when available.

This preserves architectural separation while avoiding the premature introduction of mandatory production semantics.

# 19. Continuation Point — Step 17

Step 16 resolves the immediate question of whether a non-execution reason must universally accompany `NOT_EXECUTED`.

The next architectural question should therefore move one level upward.

### Step 17 Research Question

> **Is the execution-result and capability model discovered during Phase 2E-5 sufficiently generic to support capabilities beyond transliteration, or are some of its semantics specific to transliteration?**

The investigation should determine whether the current model describes:

```text
Transliteration Architecture
```

or something more general:

```text

```

This distinction is important before the model is promoted into a standardized Core Engine contract.

The next experiment should therefore remain isolated and should not modify production code.
