## 1. Posisi Phase 2D-3



Phase 2D-3 merupakan kelanjutan langsung dari:



```text

Phase 2D-1 — Contract Inventory

        ↓

Phase 2D-2 — Behavior Classification

        ↓

Phase 2D-3 — Test Boundary & API Contract

        ↓

Test Matrix

        ↓

```



Phase 2D-1 menginventarisasi kontrak yang telah terbentuk.



Phase 2D-2 mengklasifikasikan behavior berdasarkan jenis dan tingkat kematangannya.



Phase 2D-3 menjawab pertanyaan berikut:



> **Dari boundary mana Core Transliteration Subsystem harus diuji?**



---



# 2. Latar Belakang



Setelah Contract Inventory dan Behavior Classification, telah diketahui bahwa Transliteration Subsystem memiliki beberapa jenis aturan:



- public behavior;

- architectural contract;

- implementation detail;

- open decision.



Konsekuensinya, tidak semua bagian subsystem boleh dijadikan primary test target.



Test harus masuk melalui boundary yang:



1. cukup stabil;

2. merepresentasikan behavior publik;

3. tidak bergantung pada UI;

4. tidak mengunci implementation detail;

5. tetap memungkinkan ScriptPack mempertahankan ownership atas pengetahuan linguistik.



---



# 3. Kandidat Test Boundary



Tiga kandidat boundary dipertimbangkan.



## Option A — ScriptPack Langsung



```text

Test

 ↓

JavaneseScriptPack

 ↓

transliterate(...)

```



Pendekatan ini sederhana, tetapi berisiko mencampurkan terlalu banyak tanggung jawab:



```text

Script Data

+

Linguistic Rules

+

Generic Transliteration Orchestration

```



ScriptPack tetap merupakan pemilik data dan aturan linguistik spesifik aksara, tetapi tidak secara otomatis harus menjadi satu-satunya public orchestration boundary.



---



## Option B — Application Service



```text

Test

 ↓

Transliteration Service

 ↓

ScriptPack

```



Application layer merupakan tempat use-case orchestration.



Namun Core Transliteration behavior tidak seharusnya bergantung pada Application layer hanya agar dapat diuji.



Pendekatan ini juga berisiko memindahkan logic domain ke layer yang tidak tepat.



Karena itu, Application Service tidak dipilih sebagai primary boundary untuk Core Test Contract.



---



## Option C — Dedicated Core Transliteration API



```text

Test

 ↓

Core Transliteration API

 ↓

ScriptPack

```



Pendekatan ini paling konsisten dengan arsitektur:



```text

UI

 ↓

Application

 ↓

Core Transliteration Boundary

 ↓

ScriptPack

```



Dengan pembagian tanggung jawab:



```text

Core

    ↓

Generic transliteration mechanism



ScriptPack

    ↓

Script-specific linguistic knowledge



Application

    ↓

Use-case orchestration



UI

    ↓

Presentation and interaction

```

# 4. TD-001 — Primary Test Boundary



## Keputusan



> **Core Transliteration API menjadi primary boundary untuk Core Test Contract.**



Status:



> **LOCKED**



---



## Alasan



Core Test Contract harus dapat menguji transliteration behavior tanpa mengetahui:



- struktur tokenizer;

- algoritma resolver;

- jumlah internal helper;

- bentuk token internal;

- algoritma scanning;

- detail composer.



Test cukup mengetahui:



```text

Input

    ↓

Core Transliteration API

    ↓

Observable Result

```



---



# 5. TD-002 — Explicit Request Context



## Keputusan



Operasi transliterasi secara konseptual membutuhkan:



```text

Transliteration Request

        │

        ├── text

        ├── direction

        └── script context

```



Status:



> **LOCKED**



---



## 5.1 Text



`text` merupakan input asli yang akan ditransliterasikan.



Input dapat berupa:



- Latin;

- Javanese;

- whitespace;

- punctuation;

- kombinasi karakter lain sesuai contract.



---



## 5.2 Direction



Arah transliterasi harus explicit secara konseptual.



Contoh:



```text

Latin

  ↓

Javanese

```



atau:



```text

Javanese

  ↓

Latin

```



Core tidak boleh bergantung pada tebakan implisit dari UI sebagai dasar utama arah operasi.



---



## 5.3 Script Context



Operasi transliterasi harus mengetahui ScriptPack yang menyediakan pengetahuan linguistik.



Namun mekanisme teknis belum dikunci secara berlebihan.



Script context dapat mengikuti arsitektur repository, misalnya melalui:



- ScriptPack instance;

- script identifier;

- active ScriptPack yang telah di-resolve oleh Core.



Keputusan Phase 2D-3 hanya mengunci kebutuhan konseptual terhadap context, bukan bentuk class final.



---



# 6. TD-003 — Structured Result Boundary



## Keputusan



> **Hasil operasi transliterasi harus mampu menyampaikan output dan diagnostic information tanpa bergantung pada UI.**



Status:



> **LOCKED**



---



## 6.1 Konsep Result



Boundary hasil secara konseptual:



```text

Transliteration Result

        │

        ├── output

        └── diagnostics

```



Output menyampaikan hasil transliterasi.



Diagnostics menyampaikan informasi mengenai kondisi yang ditemukan selama processing.



---



## 6.2 Mengapa Bukan String Saja?



Return value berupa `str` saja tidak cukup untuk kebutuhan subsystem apabila terdapat kondisi yang perlu dilaporkan.



Contoh konseptual:



```text

Input

    ↓

Processing

    ↓

Output

+

Diagnostic Information

```



Dengan Result boundary:



```text

Core

    ↓

Produces information

```



sedangkan:



```text

Application / UI

    ↓

Decides what to do with it

```



Core tidak boleh secara langsung:



- menampilkan dialog;

- menulis pesan ke UI;

- melakukan persistence;

- menentukan presentation behavior.



---



# 7. Diagnostic Boundary



Diagnostic merupakan bagian dari informasi hasil processing, bukan presentation.



Secara konseptual:



```text

Core Transliteration

        ↓

Detect condition

        ↓

Create diagnostic information

        ↓

Return result

```



Caller kemudian dapat:



```text

Diagnostic

    ↓

Display warning



Diagnostic

    ↓

Log information



Diagnostic

    ↓

Ignore if appropriate

```



---



## 7.1 Kontrak Diagnostic



Diagnostic secara konseptual dapat memiliki informasi seperti:



```text

Diagnostic

    ├── code

    ├── message

    └── position / context

```



Namun bentuk class final belum dikunci pada tahap ini.



Prinsip:



```text

Diagnostic Meaning

        ↓

Public Contract



Diagnostic Representation

        ↓

Implementation Decision

```

# 9. Test Boundary



Primary Core Test Contract akan masuk melalui:



```text

Input

+

Direction

+

Script Context

        ↓

Core Transliteration API

        ↓

Result

        │

        ├── Output

        └── Diagnostics

```



Dengan demikian, primary regression tests tidak perlu bergantung pada:



```text

tokenizer.scan()

resolver.resolve()

composer.compose()

```



Komponen internal dapat memperoleh unit test tersendiri jika memiliki kompleksitas yang memang memerlukan perlindungan.



Namun komponen tersebut bukan primary public regression boundary.
